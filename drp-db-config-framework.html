PART 01

로컬 Oracle 19c 구축

DRP 운영 환경과 동일한 Oracle 19c를 각자 PC에 Docker로 구성 — 공용 DB 없이 마이그레이션 스크립트·쿼리 사전 검증 가능. 실제 구축 과정에서 막힌 지점 정리. (예상 소요시간 30–40분 · Windows 11 x64 기준 · Oracle SSO 계정 필요)

1.01

사전 확인 — CPU 아키텍처

Docker Desktop 설치 파일: amd64 / arm64 두 버전. 사내 지급 PC는 거의 전부 x64(AMD64) — 헷갈리면 아래 명령으로 확인.

PowerShell
$env:PROCESSOR_ARCHITECTURE
TIP

결과 AMD64 → amd64 버전 다운로드. Surface Pro X 등 ARM 기반 기기가 아니면 대부분 이 경우.

1.02

Docker Desktop 설치

설치 파일 기본 위치: C드라이브. 명령줄 옵션으로 다른 드라이브 지정 가능 — C드라이브 여유공간 부족 시 처음부터 D드라이브 지정 권장.

파일명에 공백 포함 — & 호출 연산자 + 따옴표 필수. 경로만 입력 시 "용어가 인식되지 않습니다" 오류.

PowerShell · Downloads 폴더 기준
& "C:\Users\<계정명>\Downloads\Docker Desktop Installer.exe" install --installation-dir=D:\Docker
1.03

PATH 반영 확인

설치 스크립트가 사용자 PATH에 Docker 경로 자동 추가 — 단, 설치 전에 이미 열려 있던 터미널은 미반영. 새 PowerShell 창 열기 또는 아래 명령으로 현재 세션만 즉시 갱신.

PowerShell
$env:PATH = [Environment]::GetEnvironmentVariable("PATH","Machine") + ";" + [Environment]::GetEnvironmentVariable("PATH","User")
docker version
1.04

디스크 용량 여유 확보 (WSL2)

Docker Desktop 앱은 D드라이브 설치 가능. 단, 실제 이미지·컨테이너 데이터가 담기는 WSL2 가상디스크(docker_data.vhdx)는 기본적으로 C드라이브 생성. Oracle 19c 이미지만 12GB 안팎 — C드라이브 여유공간 사전 확인 필요.

PowerShell · 가상디스크 위치 확인
Get-ChildItem "$env:LOCALAPPDATA\Docker\wsl" -Recurse -Filter "*.vhdx" |
  Select-Object FullName, @{n='SizeGB';e={[math]::Round($_.Length/1GB,2)}}
주의

C드라이브 여유공간 부족 시 Docker Desktop → 설정(⚙) → Resources → Advanced → Disk image location에서 D드라이브 경로로 변경 후 Apply & restart. 기존 데이터 포함 자동 이전.

1.05

Oracle Container Registry 로그인

Oracle 공식 이미지 — 라이선스 동의 절차 필수, 이후 pull 허용.

① 브라우저로 container-registry.oracle.com 접속 → Oracle 계정으로 로그인 → Database → enterprise 리포지토리 진입 → Continue 클릭(라이선스 동의).

② 이후 터미널에서 로그인:

PowerShell
docker login container-registry.oracle.com
가장 많이 막히는 지점

Username은 Oracle 계정 이메일. Password 칸에 평소 로그인 비밀번호 입력 시 "unauthorized: Auth failed" 거부. Oracle 계정 설정에서 발급하는 Auth Token 입력 필요.

1.06

19c 이미지 Pull

레지스트리 페이지의 latest 태그는 현재 Oracle 26ai 지칭 — 19c 필요 시 태그 명시 필수.

PowerShell
docker pull container-registry.oracle.com/database/enterprise:19.3.0.0

이미지 용량 (다운로드 3.6GB / 디스크 상 12GB) — 회선에 따라 10~20분 소요.

1.07

컨테이너 실행

SID·PDB명: 팀 컨벤션에 맞춰 변경 또는 아래 값 그대로 사용.

PowerShell
docker run -d --name oracle19c `
  -p 1521:1521 -p 5500:5500 `
  -e ORACLE_SID=ORCLCDB `
  -e ORACLE_PDB=ORCLPDB1 `
  -e ORACLE_PWD=<SYS_비밀번호> `
  -e ORACLE_CHARACTERSET=AL32UTF8 `
  -v oracle-data:/opt/oracle/oradata `
  container-registry.oracle.com/database/enterprise:19.3.0.0
비밀번호 정책

Oracle 기본 정책: 8자 이상 + 대문자 1개 이상 + 소문자 1개 이상 + 숫자 1개 이상 필수. 미충족 시 DB 생성 진행 중(10분 이상 경과 후) 실패 — 사전 확인 필요.

캐릭터셋 확인

ORACLE_CHARACTERSET=AL32UTF8는 예시 값. 운영 DB 캐릭터셋과 반드시 일치시켜야 함(생성 후 변경 어려움) — 운영에서 아래 쿼리로 미리 확인 후 값을 맞출 것.

SQL · 운영 DB에서 확인
SELECT * FROM NLS_DATABASE_PARAMETERS WHERE PARAMETER = 'NLS_CHARACTERSET';
1.08

기동 확인

최초 DB 생성: 10~15분 소요. 상태·로그 동시 확인.

PowerShell
docker ps -a --filter "name=oracle19c" --format "table {{.Status}}"
docker logs -f oracle19c

로그 DATABASE IS READY TO USE! + 상태 (healthy) 전환 → 완료.

1.09

도커 설치 완료

컨테이너 기동 + 이미지 다운로드 후 Docker Desktop 확인 결과. Containers 탭 — oracle19c 컨테이너, 1521 포트. Images 탭 — 19.3.0.0 이미지, 12.11GB.

1.10

접속 정보 & DSNT 계정 생성

Host
localhost
Port
1521
Service (PDB)
ORCLPDB1
기본 계정
sys / system
EM Express
https://localhost:5500/em

DRP 운영 DB 메인 스키마명: DSNT. 로컬도 동일 이름 계정 생성 권장 — 혼동 방지.

SQL · PDB(ORCLPDB1) 접속 상태에서 실행
CREATE USER DSNT IDENTIFIED BY <DSNT_비밀번호>
  DEFAULT TABLESPACE USERS
  TEMPORARY TABLESPACE TEMP
  QUOTA UNLIMITED ON USERS;

GRANT CONNECT, RESOURCE TO DSNT;
GRANT CREATE VIEW, CREATE SEQUENCE, CREATE PROCEDURE, CREATE TRIGGER, CREATE SYNONYM TO DSNT;
GRANT UNLIMITED TABLESPACE TO DSNT;

개인 로컬 샌드박스 · 권한 관리 번거로우면 GRANT DBA TO DSNT;로 간단 처리 가능 (운영 DB와 무관).

1.11

스키마 복제 — Database Copy

DSNT가 참조하는 테이블·뷰·시퀀스 등을 로컬에도 만들어야 실제 프로시저 로직을 그대로 검증할 수 있음. 운영 계정에 Data Pump 디렉토리 권한이 없는 경우가 많아, SQL Developer의 Database Copy 기능으로 복제.

SQL Developer에서 운영·로컬 두 접속을 모두 열어둔 상태에서 Tools → Database Copy 실행 → Source(운영 DSNT) → Destination(로컬 DSNT) → 복사할 오브젝트 타입에 TABLE, VIEW, SYNONYM, SEQUENCE, INDEX 체크.

주의

Database Copy는 VIEW·SYNONYM을 자주 누락시킴. 복사 후 반드시 개수 비교해서 빠진 게 없는지 확인 (1.15절 참고).

1.12

GET_DDL로 뷰·시노님 보완

Database Copy가 빠뜨린 View·Synonym은 DBMS_METADATA.GET_DDL로 직접 추출해서 보완.

SQL · 운영 DB에서 실행
SELECT DBMS_METADATA.GET_DDL('VIEW', view_name, 'DSNT') AS ddl
FROM all_views
WHERE owner = 'DSNT'
ORDER BY view_name;

시노님은 'SYNONYM', 혹시 패키지·타입까지 다룰 경우 OBJECT_TYPE 값 주의 — PACKAGE BODY → 'PACKAGE_BODY', PACKAGE → 'PACKAGE_SPEC', TYPE → 'TYPE_SPEC'.

가장 많이 막히는 지점

SQL Developer 그리드 결과를 Ctrl+C로 복사하면 결과에 큰따옴표가 섞여 붙어서 실행이 안 됨. 그리드 Ctrl+C가 CSV 규칙에 따라 줄바꿈 있는 CLOB 값(GET_DDL 결과처럼 여러 줄인 텍스트)을 통째로 큰따옴표로 감싸버리기 때문. 애초에 그리드를 거치지 않고 SPOOL로 파일에 직접 출력하면 이 문제 자체가 안 생김.

SQL · F5(Run Script)로 실행
SET LONG 1000000
SET LONGCHUNKSIZE 1000000
SET PAGESIZE 0
SET LINESIZE 32767
SET TRIMSPOOL ON
SET FEEDBACK OFF
SET HEADING OFF
SET ECHO OFF
SET TERMOUT OFF

SPOOL C:\temp\dsnt_views.sql

SELECT DBMS_METADATA.GET_DDL('VIEW', view_name, 'DSNT') || ';'
FROM all_views
WHERE owner = 'DSNT'
ORDER BY view_name;

SPOOL OFF

반드시 F5(Run Script)로 실행 — F9/그리드 조회로는 SPOOL이 작동 안 함. || ';'로 세미콜론을 미리 붙여둬야 나중에 실행할 때 ORA-00933 에러 없이 바로 돌아감.

1.13

부계정 생성과 참조 권한

DSNT 프로시저가 같은 운영 DB 안의 다른 스키마(예: NPTNR·DAMO 같은 부계정)를 참조하는 경우, 로컬에도 그 계정을 똑같이 만들고 필요한 권한만 내주면 됨.

SQL · 부계정 생성 예시(NPTNR)
CREATE USER NPTNR IDENTIFIED BY <NPTNR_비밀번호>
  DEFAULT TABLESPACE USERS
  TEMPORARY TABLESPACE TEMP
  QUOTA UNLIMITED ON USERS;

GRANT CONNECT, RESOURCE TO NPTNR;

DSNT가 실제로 참조하는 오브젝트만 골라서 권한 부여 (NPTNR 계정으로 접속해서 실행):

SQL · NPTNR 접속 상태에서 실행
GRANT SELECT ON TCM_USER_M TO DSNT;
GRANT EXECUTE ON FN_CM_COMM_NM TO DSNT;
TIP

개인 로컬 샌드박스면 권한 하나하나 내주는 대신 GRANT DBA TO NPTNR;로 간단히 처리해도 무방 (1.10절과 동일한 이유).

1.14

재컴파일

부계정을 나중에 추가하면 이미 만들어둔 DSNT 오브젝트가 INVALID 상태로 남아있을 수 있음 — UTL_RECOMP로 재컴파일. 참조 관계가 있는 스키마부터 순서대로.

SQL · 로컬 DB에서 실행
EXEC UTL_RECOMP.RECOMP_SERIAL('NPTNR');
EXEC UTL_RECOMP.RECOMP_SERIAL('DSNT');
1.15

운영 vs 로컬 오브젝트 비교

복제가 제대로 됐는지 확인하려면 운영·로컬에서 같은 쿼리를 각각 돌려서 결과를 대조.

SQL · 운영·로컬 각각 실행
SELECT owner, object_type, status, COUNT(*) AS cnt
FROM all_objects
WHERE owner IN ('DSNT', 'NPTNR')
GROUP BY owner, object_type, status
ORDER BY owner, object_type, status;
가장 많이 막히는 지점

ALL_OBJECTS는 접속 계정이 볼 수 있는 오브젝트만 보여줌(본인 소유 + 권한 있는 것). DSNT 계정으로 조회하면 NPTNR 오브젝트가 안 보여서 비교가 왜곡될 수 있음 — SYSTEM 계정으로 조회하거나, 비교용으로만 GRANT DBA TO DSNT; 부여 후 재접속해서 조회 (롤 부여는 새 세션부터 적용).

1.16

배포 리허설용 백업·복원

배포 스크립트를 로컬에서 여러 번 반복 리허설하고 싶으면, 매번 컨테이너를 처음부터 다시 만들지 말고 oracle-data 볼륨만 스냅샷 떠뒀다가 복원하는 게 훨씬 빠름.

PowerShell · 백업 (컨테이너 정지 후)
docker stop oracle19c

docker run --rm -v oracle-data:/data -v ${PWD}:/backup busybox `
  tar czf /backup/oracle_backup.tar.gz -C /data .

docker start oracle19c
PowerShell · 복원
docker stop oracle19c

docker run --rm -v oracle-data:/data busybox sh -c "rm -rf /data/*"

docker run --rm -v oracle-data:/data -v ${PWD}:/backup busybox `
  tar xzf /backup/oracle_backup.tar.gz -C /data

docker start oracle19c

이 방식이면 컨테이너 재생성 없이 데이터만 원상복구되어, 배포 스크립트 리허설을 몇 번이고 반복해도 처음 세팅한 상태로 빠르게 되돌릴 수 있음.

1.17

트러블슈팅 모음

실제 발생 증상·해결 순서 그대로. 동일 메시지 발생 시 아래에서 확인.

증상원인해결
'Docker' 용어가 인식되지 않음 실행파일명 공백을 셸이 토큰 분리 & 호출 연산자 + 전체 경로를 따옴표로 감싸기
설치 후 docker 명령 인식 안 됨 설치 전부터 열려 있던 셸이라 PATH 미반영 새 창 열기 또는 $env:PATH 수동 갱신
unauthorized: Auth failed Password 칸에 일반 로그인 비밀번호 입력 Oracle 계정에서 발급한 Auth Token 사용
docker-credential-desktop not found Git Bash 등 다른 셸의 PATH에 Docker bin 미포함 PATH에 D:\Docker\resources\bin 추가
C드라이브 용량 급감 WSL2 가상디스크가 기본적으로 C드라이브에 생성 Settings → Resources → Advanced에서 위치 이전
DB 생성 중간에 실패 ORACLE_PWD가 비밀번호 복잡도 미충족 대문자+소문자+숫자 포함 8자 이상으로 재실행
PART 02

drp-db 형상관리 프레임워크

관리 대상 제외: 테이블 DDL(V파일) - 파일 생성 순서가 중요하여 운영난이도 있음

관리 대상: PROCEDURE / FUNCTION / PACKAGE / TRIGGER — CREATE OR REPLACE 가능 오브젝트, Flyway R파일(Repeatable Migration)로 형상관리. drp-db/README.md 기준 + PART 01 로컬 Oracle 19c 실연동 확인 반영.

Flyway 라이선스 정책 정리

일반 Java/Spring 프로젝트 개발·배포: Flyway Community Edition — 무료, 상업적 이용 가능.
기업 차원 복잡한 배포 통제, 롤백(Undo) 자동화, 구버전 DB 지원 필요 시: Flyway Enterprise 구독 검토 대상.
drp-db는 전자(일반 개발/배포) 해당 — Community Edition으로 충분.

2.04

R파일 작성 규칙

파일명 규칙: R__<설명>.sql (언더스코어 2개 필수 — 누락 시 Flyway 미인식).

오브젝트파일 분리
PROCEDURE / FUNCTION / TRIGGER1개 / 파일
PACKAGE (Oracle 전용)SPEC/BODY 2개 파일, 1_/2_ 순번으로 SPEC이 먼저 실행되도록
주의

MariaDB 프로시저/함수/트리거 — DELIMITER 필수. BEGIN ... END 내 세미콜론 포함 시 Flyway MySQL 파서가 문장 오분리 → 문법 오류.

SQL · mysqldump 스타일
DELIMITER //

CREATE OR REPLACE PROCEDURE PRC_HELLO()
BEGIN
    SELECT 'Hello from drp-db Flyway migration' AS message;
END //

DELIMITER ;

2.07

접속정보 암호화

db.targets 접속정보(url/username/password): 평문 아님, drp-cm과 동일 방식(Jasypt AES-256 + SaltType.ZERO) 암호화. 키/솔트 파일도 drp-cm 것 재사용 (src/main/resources/etc/{key1,key2,salt1,salt2}.ini).

복호화: DataSourceConfig가 CryptoService.decAES(value, true, SaltType.ZERO)로 기동 시 자동 수행. MariaDB·Oracle 동일 방식.

신규 접속정보 암호화: CryptoService.getInstance(...).encAES(평문) 1회 호출 → 결과값 application.yaml에 입력.

JDBC URL 주의

Oracle URL 형식: jdbc:oracle:thin:@<host>:<port>/<service>. jdbc:log4jdbc:oracle:thin:@... 형식은 log4jdbc 의존성 부재로 "No suitable driver" 오류 차단.

2.08

INVALID 오브젝트 점검 (+ 자동 재컴파일)

R파일 참조 패키지/함수/테이블 부재 시에도 Flyway migrate() 자체는 성공 가능 — 컴파일은 되지만 오브젝트 상태 INVALID.
대표 사례: 프로시저 A를 호출하는 프로시저 B가 A보다 먼저 생성.
원인: R파일 실행 순서는 이름(설명) 알파벳순뿐, 호출관계 무관. A 생성 후에도 B는 자동 VALID 전환 안 됨 — B 실제 호출 시점에 Oracle이 자동 재컴파일 시도 (로컬 재현 확인).

MigrateRunner: Oracle 타겟 마이그레이션 종료 시마다 InvalidObjectChecker 호출. db.recompile-check-enabled 값별 동작 구분:

recompile-check-enabled동작
true ① user_objects에서 INVALID 오브젝트 조회 → ② ALTER {PROCEDURE|FUNCTION|PACKAGE|PACKAGE BODY|TRIGGER} ... COMPILE로 재컴파일 시도(최대 5회 반복, A→B→C 연쇄 대비) → ③ 그래도 남은 것만 경고 로그
false 재컴파일 시도 없이 ①·③만 수행 — 기동 속도는 그대로 지키면서 INVALID 목록은 항상 로그에 남김
실행 로그 예시
INFO  InvalidObjectChecker : [oracle-dsnt] 재컴파일로 정상화된 오브젝트 1건 (생성 순서 문제로 추정)
WARN  InvalidObjectChecker : [oracle-dsnt] INVALID 오브젝트 1건:
  - [PROCEDURE] SP_SE_IFSEWM0110
참고

동일 배포 내 순서 문제로만 INVALID였던 오브젝트는 자동 정리, 실제 문법/참조 오류만 최종 경고로 잔존. 빌드 실패로는 이어지지 않음 — 매번 콘솔/로그 확인 필요.

직접 조회:

SQL
SELECT object_name, object_type, status
FROM user_objects
WHERE status = 'INVALID';

-- 구체적인 컴파일 에러
SELECT name, type, line, position, text
FROM user_errors
WHERE name = '<오브젝트명>'
ORDER BY sequence;
2.09

배포 중 락 대기 (DDL_LOCK_TIMEOUT)

CREATE OR REPLACE는 대상 오브젝트에 배타적 DDL 락 필요.

실패 시나리오

스케줄러 잡이 해당 프로시저 실행 중이면 Oracle 기본값(DDL_LOCK_TIMEOUT = 0)에서 대기 없이 즉시 ORA-04021: timeout occurred while waiting to lock object 실패 — 해당 R파일은 flyway_schema_history에 failed로 잔존.

타겟별 ddlLockTimeoutSeconds 설정 시 FlywayConfig가 Flyway 커넥션에 ALTER SESSION SET DDL_LOCK_TIMEOUT = <초> 실행 — 락 획득 실패해도 즉시 실패 대신 설정 시간만큼 대기 후 재시도.

참고

대기 시간 내 잡이 끝나지 않으면 결국 동일하게 ORA-04021 발생 — 완전 회피가 아니라 유예 확보.

2.10

마이그레이션 실패 복구

DRP-DB는 어플리케이션 기동시 flyway.repair() 수행

R파일 실행 실패 시 Flyway가 flyway_schema_history에 실패 기록 — 이후 모든 실행 검증(validate) 단계에서 차단.

  1. 문제 SQL 스크립트 수정
  2. --repair 옵션 1회 실행 — 실패 이력 정리
Bash
./gradlew bootRun --args='--spring.profiles.active=local --repair'
2.11

프로시저 일괄 추출

기존 스키마 프로시저 R파일 온보딩 전, DB 내 SP_SE% 프로시저 소스 로컬 파일 추출 방법. DBMS_METADATA.GET_DDL + SPOOL 2단계 조합.

① 세션 포맷 설정 — PL/SQL 오브젝트는 기본값이 이미 CREATE OR REPLACE 형태, PRETTY/SQLTERMINATOR만 활성화.

SQL
BEGIN
  DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM, 'SQLTERMINATOR', TRUE);
  DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM, 'PRETTY', TRUE);
END;
/
삽질 포인트

'REPLACE' 파라미터명 입력 시 ORA-31600 발생 — 존재하지 않는 파라미터, 불필요. PROCEDURE/FUNCTION/PACKAGE/TRIGGER는 GET_DDL 기본 출력에 CREATE OR REPLACE 이미 포함.

② 프로시저 개수만큼 SPOOL 스크립트 생성 — 이름당 파일 하나(R__<이름>.SQL) 추출 스크립트 SQL로 선(先) 생성.

SQL
SET LINESIZE 32767
SET LONG 1000000
SET PAGESIZE 0
SET FEEDBACK OFF
SET HEADING OFF
SET VERIFY OFF
SET TRIMSPOOL ON
SET ECHO OFF

SPOOL C:\temp\gen_sp_se_export.sql

SELECT 'SPOOL C:\temp\R__' || object_name || '.SQL' || CHR(10) ||
       'SELECT DBMS_METADATA.GET_DDL(''PROCEDURE'', ''' || object_name || ''') FROM DUAL;' || CHR(10) ||
       'SPOOL OFF'
FROM user_objects
WHERE object_type = 'PROCEDURE'
  AND object_name LIKE 'SP_SE%'
ORDER BY object_name;

SPOOL OFF
SQL Developer 삽질 포인트

SQL Developer는 SQL*Plus와 달리 스크립트 실행(F5) 필수 — SPOOL 동작 조건(Ctrl+Enter 실행 시 무시). 실행 중 페이지 전환마다 컬럼 헤더·구분선(---) 결과 사이 혼입 → 스크립트 오염 사례 — SPOOL/SELECT DBMS_METADATA 시작 줄만 필터링 후 실행(grep -E "^(SPOOL |SELECT DBMS_METADATA)").

③ 생성된 스크립트 실행 — 정리된 스크립트 @ 실행 → C:\temp에 프로시저 개수만큼 R__SP_SE_xxx.SQL 파일 생성.

SQL
@C:\...\gen_sp_se_export_clean.sql
영향도

전 과정 조회(SELECT) + 세션 설정뿐 — DB 흔적 없음. INSERT/UPDATE/DELETE/DDL 없어 커밋·롤백 개념 미적용, 타 세션 영향 락도 없음. SET_TRANSFORM_PARAM 역시 세션 종료 시 자동 소멸하는 세션 로컬 설정.

주의

추출용 헬퍼 스크립트(gen_sp_se_export*.sql)는 sql/oracle/repeatable/dsnt/procedure/ 배치 금지 — drp-db가 flyway.migrate() 시 실제 스캔하는 위치(2.03절 참고). 추출된 R__*.SQL 파일도 검증 완료 후에만 해당 폴더 이동 — 이동 즉시 Flyway 관리 대상 전환.
