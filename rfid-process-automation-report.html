01
머지 자동화 · 판정 로직

체크아웃 없는 상태 판정, 안전한 케이스만 자동 처리

레포별 상태를 4가지로 분기하여 안전한 케이스만 자동 처리하고, 위험한 케이스는 사람에게 위임. main과 rfid-develop의 공통 조상 커밋(merge-base)을 기준으로 두 브랜치의 위치 관계를 판정.

1main == merge-base (main의 모든 커밋이 이미 반영됨)
→
건너뜀
2rfid-develop == merge-base (fast-forward 가능)
→
커밋 해시로 직접 push
3양쪽 독자 커밋 존재, merge-tree 충돌 없음
→
임시 worktree에서 머지 후 push
4양쪽 독자 커밋 존재, merge-tree 충돌 있음
→
자동 처리 중단, 수동 목록에 기록

핵심은 git merge-tree --write-tree(Git 2.38+)로 실제 checkout 없이 충돌 여부를 먼저 확인하고, 머지가 필요한 경우(케이스 3)에만 git worktree add로 별도 작업공간을 만들어 그 안에서만 머지·push를 수행한 뒤 worktree를 정리하는 흐름. 스크립트 실행 중에도 현재 작업 중인 파일·브랜치 상태에는 영향 없음.

머지 자동화 · 실행 결과

실제 실행 로그와 자동 처리 캡처

실행 예시 — drp-se 레포 실제 로그
[drp-se] 처리 시작
  remote: origin
  fetch 중...
  ↕ diverged (main +3개, rfid-develop +1개 독자 커밋)
  → 충돌 여부 확인 중...
  ✓ 충돌 없음 → 자동 머지 진행

사람 개입 없이 스케줄러가 트리거되어 11개 레포를 순회 처리한 실행 화면. drp-hr에서 diverged 상태를 감지해 자동 머지·push까지 완료한 사례 (다음 슬라이드 캡처).

    브랜치 참조 대신 커밋 해시를 push 대상으로 지정

01
커밋 규칙 · 스킬 구조화

커밋 메시지 양식·표현을 Claude Code 스킬로 자동화

Conventional Commits 표준을 그대로 쓰지 않고,
이 프로젝트 계층 구조(Controller-Service-DAO + Nexacro 화면)에서 실제 쓰이는 5 type/4 scope만 남겨 커밋마다 type을 고민하는 시간을 줄이고, 화면ID 표기 규칙을 추가.
이 규칙을 SKILL.md로 구조화해 Claude Code가 커밋 작성·검토 시 참조하도록 구성.

구성 흐름
Source
개발 WBS 문서
→
Extract
화면ID·화면명 항목 추출
→
Structure
program-list-screens.md
program-list-interfaces.md
→
Apply
commit-convention SKILL.md 규칙 적용
→
Query
git log --grep로 화면 단위 조회

별도로 화면 목록을 새로 만드는 대신, 이미 존재하는 개발 WBS 문서의 화면 항목(화면ID·화면명·담당 모듈)을 추출해 program-list-screens.md / program-list-interfaces.md로 정리. Claude Code는 화면 작업을 시작하기 전 이 목록에서 화면ID를 먼저 조회하도록 규칙화되어 있음.

02
커밋 규칙 · 스킬 구조화

규칙 설계 과정 1~2단계

  1. 1단계
    계층 구조를 type/scope로 매핑 실제 코드 구조(Controller-Service-DAO + Nexacro 화면)를 기준으로 scope 4종(controller/service/dao/ui)을 먼저 확정하고,
    Conventional Commits의 type 중 이 구조에서 실제로 발생하는 작업만 남겨 5종으로 축소
    feat
    신규 기능
    fix
    버그 수정
    refactor
    구조 개선 (동작 변화 없음)
    perf
    성능 개선
    chore
    설정 등 그 외 작업
  2. 2단계 커밋 단위를 관련 작업 단위로 분리여러 화면·여러 목적의 변경을 한 커밋에 몰아 담지 않고,
    화면 또는 기능 단위로 커밋을 쪼개도록 함
    — 커밋을 분리해야 화면명[화면ID] 표기와 git log --grep 조회가 화면 단위로 정확히 맞아떨어짐.
    화면과 무관한 변경(공통 로직, 의존성 등)은 별도 커밋으로 분리해 화면 커밋과 섞이지 않게 함
03
커밋 규칙 · 스킬 구조화

규칙 설계 과정 3~4단계

  1. 3단계 화면 수에 따라 화면ID 표기 위치를 분기그럼에도 한 커밋에 화면이 여러 개 걸리는 경우,
    제목에는 요약만 쓰고 본문의 파일별 항목 앞에 화면명[화면ID]를 붙이도록 규칙을 나눔
    — 제목에 화면ID를 나열하면 git log --oneline 가독성이 떨어지는 문제를 확인한 뒤 정한 기준
  2. 4단계 좋은 예/나쁜 예로 규칙을 검증파일명 중복 나열, 코드 식별자 노출, 50자 초과 등
    실제 커밋에서 나올 수 있는 경계 사례를 좋은 예/나쁜 예 쌍으로 SKILL.md에 포함시켜,
    규칙 문장만으로는 애매한 부분을 예시로 보완
SKILL.md 전문 보기 (별도 파일) .claude/skills/commit-convention/SKILL.md
